# 캐릭터 카드·Lorebook·역할 학습 조사

공식 문서, 공개 명세, 구현 코드와 논문 초록/공식 저장소를 구분해서 조사했다. 아래의 제품 동작은 확인한 문서 기준이며, 이 구성이 현재 Qwen3-1.7B의 한국어 품질을 해결한다는 실험 결과는 아니다. 애플리케이션·프롬프트·가중치는 변경하지 않았다.

## 1. 결론

사용자가 제안한 `공통 세계관 + 소속 학교/동아리 + 개인 특징 + 공통 지침` 조합은 기존 캐릭터 챗 도구의 Character Card + World Info/Lorebook 구조와 상당히 가깝다.

다만 다음은 수정하는 것이 좋다.

1. AI 캐릭터 카드와 **사용자 정체성(User Persona)**을 별도로 둔다. 우리 앱에서는 사용자를 선생님으로 고정한다.
2. 말투를 LoRA로만 옮기지 않는다. 카드의 최소 말투 정보와 대화 예시는 남기고, LoRA는 검증된 경우에 추가한다.
3. 학교/동아리 계층은 프롬프트의 권한 계층이 아니라 **자료 재사용을 위한 참조 관계**다.
4. 핵심 정체성은 항상 포함하고, 긴 설정은 관련성·예산에 따라 선택한다. 모든 관계 인물을 항상 넣지 않는다.
5. 현재 대화·사용자 기억·일정은 설정집이나 모델 가중치와 분리한다.
6. 카드 호환 포맷을 채택하는 것과 PEFT LoRA를 브라우저에서 실행하는 것은 별개다.

## 2. 실제 도구·명세에서 확인한 것

### SillyTavern Character Design

[공식 문서](https://docs.sillytavern.app/usage/core-concepts/characterdesign/)

- `Description`: 핵심 정체성·배경 등. 항상 프롬프트에 포함되는 정보.
- `Personality`: 성격 요약.
- `Scenario`: 대화의 전제와 상황.
- `First Message`: 최초 발화. 공식 가이드는 첫 메시지의 문체와 길이가 후속 생성에 중요하다고 강조한다. 이는 제품의 작성 가이드이지 우리 모델에 대한 통제 실험 결과는 아니다.
- `Examples of dialogue`: 캐릭터가 어떻게 말하는지 보여주는 예시. `{{user}}`와 `{{char}}`로 발화자를 구분한다.
- 예시 대화는 기본적으로 문맥 공간에 따라 밀려날 수 있고, 유지 설정도 있다. 예시가 언제나 남는다고 가정하면 안 된다.
- 이름/설명/성격/시나리오는 permanent tokens에 해당한다. 따라서 긴 설명을 넣으면 대화에 쓸 수 있는 문맥이 줄어든다.

캐릭터별 LoRA 학습은 이 카드 작성 흐름의 필수 단계가 아니다. 상세 말투와 예시를 카드에서 제거하고 LoRA만 신뢰해야 한다는 근거도 이 문서에는 없다.

주의: 문서의 RP 예시는 행동 지문·Markdown 등을 사용한다. 우리 앱은 모모톡 문자 대화이므로 **구조를 참고하되 예시 문체나 기본 RP 프롬프트를 그대로 복사하면 안 된다.**

### SillyTavern User Personas

[공식 문서](https://docs.sillytavern.app/usage/core-concepts/personas/)

SillyTavern에서 Persona는 채팅에 참여하는 **사용자의 정체성**을 뜻한다. 캐릭터 카드와 별도로 이름·설명을 관리하고, 설명을 프롬프트에 삽입할 수 있다.

우리 코드의 `persona`는 AI 캐릭터를 뜻하므로 용어를 그대로 섞으면 혼동된다. 개념상 `characterProfile`과 `userPersona`를 구분하는 것이 좋다. 구현 파일명을 전부 바꿔야 한다는 뜻은 아니다.

이번 미카 실험에서 사용자를 나기사로 부른 문제를 생각하면, `assistant=선택 캐릭터`, `user=선생님`, `나기사=설정에 등장하는 제3자`를 구별하는 설계는 직접적인 개선 후보다. 효과는 별도 비교가 필요하다.

### SillyTavern World Info / Lorebook

[공식 문서](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)

- 최근 메시지의 키워드에 따라 관련 설정을 프롬프트에 추가하는 동적 사전 방식.
- Global, Character, Persona, Chat 단위의 설정 자료를 결합할 수 있다.
- 캐릭터에 기본 Lorebook과 추가 Lorebook을 연결할 수 있다. 단, 캐릭터 카드로 내보낼 때는 기본 Lorebook만 포함된다고 문서에 명시되어 있다. **외부 공유 참조 전체가 자동으로 이식되는 것은 아니다.**
- 상시 항목, 삽입 순서, 토큰 예산, 재귀 활성화 제한 등을 제공한다.
- 키워드나 제목 등 메타데이터가 그대로 모델에게 전달되는 것은 아니다. 실제 `content`는 주어를 포함한 독립적인 설명이어야 한다.
- 공식 문서도 설정을 삽입했다고 원하는 출력이 보장되지 않으며, 모델이 추가 정보를 활용하는 능력에 달려 있다고 경고한다.

우리에게는 `공통 키보토스`, `밀레니엄`, `세미나`, `게임개발부` 등을 재사용하는 데 적합한 패턴이다. 단, 학교/동아리 의미 계층이나 캐릭터별 소속 선택을 포맷이 자동으로 이해해 주는 것은 아니다. 그 연결은 우리 앱에서 정의해야 한다.

처음에는 기존 ID 참조와 필요한 항목 선택으로 충분하다. 현재 규모에서 임베딩 서버/벡터 DB를 먼저 도입할 필요는 없다. 재귀 활성화도 처음부터 켜면 학교 → 동아리 → 구성원 → 다른 학교로 설정이 연쇄 유입될 수 있으므로 제한하는 편이 낫다.

### RisuAI

- [Lorebook wiki](https://github.com/kwaroran/RisuAI/wiki/Lorebook)
- [wiki 상태 안내](https://github.com/kwaroran/RisuAI/wiki)
- [현재 카드 구현 코드](https://github.com/kwaroran/RisuAI/blob/main/src/ts/characterCards.ts)

wiki는 최근 채팅의 activation key로 필요한 lore를 추가한다고 설명한다. 그러나 wiki 자체가 outdated라고 밝히므로 최신 UI나 기능 전체의 근거로 삼지는 않았다.

구현 코드에서는 V2/V3 카드에 다음 정보를 별도로 내보내는 것을 확인했다.

`description`, `personality`, `scenario`, `first_mes`, `mes_example`, `system_prompt`, `post_history_instructions`, `character_book`

`character_book`에는 `scan_depth`, `token_budget`, `recursive_scanning`, `entries`가 들어간다. 즉 카드 내용과 조건부 설정의 분리는 실제 다른 도구의 구현에서도 확인된다.

### Character Card V2 / V3

- [CCv2 명세](https://github.com/malfoyslastname/character-card-spec-v2/blob/main/spec_v2.md)
- [CCv3 명세](https://github.com/kwaroran/character-card-spec-v3/blob/main/SPEC_V3.md)

캐릭터 데이터 교환용 커뮤니티 명세다. 도구별 기능 지원 차이는 따로 확인해야 한다.

| 필드 | 용도 |
|---|---|
| `name`, `description` | 이름과 기본 설명 |
| `personality` | 성격 |
| `scenario` | 대화 전제 |
| `first_mes`, `alternate_greetings` | 시작 발화 |
| `mes_example` | 말투·대화 예시 |
| `character_book` | 캐릭터 관련 Lorebook |
| `system_prompt`, `post_history_instructions` | 캐릭터별 프롬프트 지시 |
| `extensions` | 애플리케이션별 추가 데이터 |

**호환성 주의:** CCv2의 비어 있지 않은 `system_prompt`는 기본 시스템 프롬프트를 대체하도록 규정되어 있고, `{{original}}`로 기존 프롬프트를 포함할 수 있다. 우리 앱의 역할·기억·기능 제약을 외부 카드가 덮어쓰도록 무조건 복제해서는 안 된다. 지원 범위를 명시하고, 외부 카드의 프롬프트/확장 스크립트를 신뢰된 운영 지시나 실행 코드로 취급하지 않아야 한다. 일부 필드만 참고하면서 완전한 규격 준수를 주장하면 안 된다.

우리의 `school_id`, `club_ids`, 어댑터 경로·베이스 revision 같은 메타데이터는 자체 내부 스키마나 이름공간을 둔 `extensions`로 관리할 수 있다. 학교/동아리 상속과 LoRA 실행은 CCv3를 채택했다고 자동으로 제공되는 기능이 아니다.

## 3. 역할 학습 연구가 말하는 범위

### RoleLLM — Findings of ACL 2024

- [논문](https://aclanthology.org/2024.findings-acl.878/)
- [공식 저장소](https://github.com/InteractiveNLP-Team/RoleLLM-public)

공식 설명은 역할 프로필, 역할별 지식/경험을 얻는 Context-Instruct, 말투 모방을 위한 RoleGPT, 이를 이용한 역할 조건부 미세조정 RoCIT를 구분한다. RoleBench는 100개 역할, 168,093개 샘플이라고 보고한다.

따라서 역할 미세조정이 반드시 순수 말투만 학습하는 작업은 아니다. 지식과 말투를 함께 학습하는 접근도 있다. 이 규모를 캐릭터별 최소 필요 데이터 수로 해석하면 안 되고, 영어/중국어 연구 성능을 현재 한국어 1.7B 모델의 보장으로 사용해서도 안 된다.

### Character-LLM — EMNLP 2023

[논문](https://aclanthology.org/2023.emnlp-main.814/)

인물의 프로필·경험·감정 상태를 학습 대상으로 삼고, 프로필을 경험 형태로 구성해 개인 시뮬레이션 모델을 학습하는 접근을 설명한다.

표면적인 어미뿐 아니라 상황별 반응과 경험 활용까지 학습 대상이 될 수 있다는 참고 사례다. 논문에서 구성한 경험 데이터를 사용하는 것과, 우리 프로젝트에서 출처가 있는 실제 게임 대사를 사용하는 것은 다른 데이터 제작 정책이다. 연구 방식을 이유로 창작 대화를 원문처럼 표시해서는 안 된다.

이 조사에서는 논문의 초록/공식 프로젝트 설명을 확인했다. 모든 실험 설정을 재현하거나 한국어·현재 모델에서 검증하지 않았다.

## 4. molu-calendar에 권장하는 최소 구조

```text
앱 공통 운영 지침
  ├─ 화자/상대 고정
  ├─ 출력 형식
  └─ 기억·일정·실행 권한의 한계

사용자 정체성: 선생님
선택 캐릭터 카드
  ├─ 정체성·성격·개인 관계
  ├─ 최소 말투 정보: register / 상대 호칭 / 자기 호칭
  ├─ 검수한 실제 대화 예시
  └─ 학교·동아리 자료 참조

공유 세계관·소속 Lorebook
  ├─ 짧은 필수 정보는 항상 포함
  └─ 긴 설정·다른 인물은 관련될 때만 추가

현재 대화 및 앱이 전달한 사실

선택적 캐릭터 LoRA — 같은 입력의 adapter off/on 비교에서 도움이 확인된 경우
```

- 자료 계층은 ID 참조/합성으로 유지한다. 아로나·프라나처럼 일반 학교/동아리 계층 밖의 캐릭터도 지원한다.
- 성격의 명세는 카드에, 그 성격이 드러나는 실제 표현/반응은 예시와 학습 데이터에 둔다.
- 구체적인 말투를 프롬프트에 넣으면 이전 지식이 반드시 깨진다는 근거는 없다. 충돌·과도한 길이·화자 모호성을 줄여야 하는 것이지, 말투 설명과 예시를 모두 없애야 하는 것은 아니다.
- LoRA는 말투만 저장하는 격리된 슬롯이 아니며 사실 답변에도 영향을 줄 수 있다. 최신 설정의 관리 원본은 계속 외부 자료로 둔다.
- 학습과 추론은 같은 프롬프트 조립 규칙을 사용한다. 학습 입력에 필요한 설정을 주고 마지막 캐릭터 답변에 loss를 적용하는 현재 구조는 유지할 수 있다.
- 학생끼리의 대화를 학습에 추가할 때 다른 학생의 발화를 곧바로 `user=선생님`으로 바꾸지 않는다. 화자 관계의 정합성을 검수해야 한다.
- 캐릭터 ID, 활성 어댑터, 그 캐릭터의 대화 이력을 일치시킨다. 데이터 재사용이 대화 이력 혼합을 뜻하지 않는다.
- 표준 카드로 내보내는 경우 외부 Lorebook 참조를 어떻게 전달할지 정한다. 원본은 공유하되 내보내기는 필요한 설정을 생성된 스냅샷으로 묶을 수 있다.

## 5. 현재 지침에서 특히 검토할 점

- `register`가 별도 데이터로 있어도 현재 `systemPromptFor()`는 직접 주입하지 않고 소개문의 표현에 의존한다.
- 사용자 정체성을 명시적으로 고정하는 구성이 부족하다.
- `AI라는 말을 하지 않는다`는 아로나·프라나 같은 설정과 충돌할 수 있다. 실제 모델 운영 이야기와 캐릭터 설정 속 AI/OS를 구분해야 한다.
- `전문 용어를 쓰지 않는다`는 아리스의 게임 용어나 캐릭터 고유 표현을 불필요하게 제한할 수 있다.
- 일률적인 1인칭 대명사 강제는 피한다. 아리스의 자기 이름 지칭과 호시노의 아저씨 호칭은 캐릭터별로 유지한다.
- 출력은 모모톡 대사다. 소설식 RP 지문을 장려하는 외부 프롬프트를 그대로 가져오지 않는다.

## 6. 적용 전 평가

같은 모델·질문·샘플링에서 다음을 비교한다.

1. 기존 카드, LoRA off.
2. 새 역할 구분/정보 조립, LoRA off.
3. 새 조립 + 검수된 train 출처 예시, LoRA off.
4. 3과 동일한 입력, LoRA on.

검증용 원문 답변은 예시로 넣지 않는다. 보존된 기존 run/card/비교 결과도 수정하지 않고 새 평가 조건으로 기록한다.

화자·상대 호칭, 말투, 질문 대응, 사실/기억, 제약 준수, 긴 대화에서의 유지 여부를 따로 평가한다. Lorebook 입력이나 새로운 카드 포맷 자체는 합격 근거가 아니다. 현재 두 어댑터의 품질 불합격 판정도 이 조사만으로 바뀌지 않는다.
