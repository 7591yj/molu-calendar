## 1. 요약

권장 구조는 **IndexedDB에 원문을 보존하고, 모델에는 최근 대화와 필요한 기억만 전달**하는 방식이다.

- IndexedDB는 AI의 기억이나 학습 기능이 아니라 **브라우저 안의 데이터베이스**다.
- 메모리는 저장된 자료를 검색·선별하여 프롬프트에 넣는 애플리케이션 기능이다.
- 캐릭터 설정/Lorebook, 개인 대화 기록, 모델 파일 캐시, GPU KV 캐시는 서로 다른 용도다.
- 첫 버전은 **원문 저장 + 최근 대화 + 사용자가 명시적으로 저장한 기억 + 범위 제한 검색**까지 구현한다.
- 자동 요약은 별도 선택 단계로 미룬다. 현재 품질이 미달인 모델의 답변을 그대로 장기 사실로 굳히지 않는다.
- MVP 범위는 현재의 **선생님과 캐릭터별 1:1 모모톡**이다. 학생끼리/그룹 대화의 실제 생성 기능, 클라우드 동기화, LoRA 브라우저 로딩은 포함하지 않는다.

## 2. IndexedDB가 무엇인가

### 2.1 쉬운 설명

`localStorage`가 사이트별 작은 문자열 보관함이라면, **IndexedDB는 사이트별로 구조화된 자료를 저장하고 조건에 따라 찾아볼 수 있는 로컬 DB**다.

예를 들어 메시지 하나를 다음처럼 저장한다.

```text
메시지 ID / 대화방 / 실제 화자 / 내용 / 전송 순서 / 시간 / 생성 출처 / 상태
```

방 ID와 순서에 인덱스를 만들어 두면 모든 대화를 읽지 않고도 “유우카 방의 최근 50개”를 조회할 수 있다. 비동기 API이며, 여러 변경을 하나의 트랜잭션으로 묶을 수 있다.

| 구분        | localStorage                               | IndexedDB                                  |
| ----------- | ------------------------------------------ | ------------------------------------------ |
| 값          | 문자열. 객체는 JSON 직렬화 필요            | 구조화된 객체·배열 등                      |
| API         | 동기식                                     | 비동기식                                   |
| 대화 추가   | 현재 코드에서는 전체 방 객체를 다시 직렬화 | 메시지 단위 추가/갱신 가능                 |
| 조회        | 키로 문자열 전체 읽기                      | 키·인덱스·커서로 범위 조회                 |
| 다중 변경   | 여러 키 사이의 원자적 트랜잭션 없음        | 지정한 object store들을 묶어 트랜잭션 처리 |
| 적합한 용도 | 작은 설정·선호                             | 대화 원문·기억·검색용 메타데이터           |

여기서 비동기라는 것은 저장 요청의 완료를 기다리는 동안 UI 작업을 계속할 수 있다는 뜻이다. 큰 자료의 복사·가공 비용까지 사라지는 것은 아니므로 페이지 조회와 제한된 처리량이 필요하다.

### 2.2 무엇을 보장하지 않는가

- 서버 DB가 아니다. 기본적으로 다른 PC·브라우저로 자동 동기화되지 않는다.
- 같은 origin에 묶인다. **프로토콜·호스트·포트**가 다르면 다른 저장소다. 개발 서버 포트를 바꿔도 이전 기록이 자동으로 보이지 않을 수 있다.
- 새로고침 후에도 남지만 영구 백업은 아니다. 사이트 데이터 삭제, 비공개 모드 종료, 저장소 축출 등으로 사라질 수 있다.
- 용량은 브라우저·기기 정책에 따라 달라진다. “항상 몇 GB를 쓸 수 있다”고 가정하지 않는다.
- `navigator.storage.persist()`는 보존 권한을 **요청**하는 API다. 승인되지 않을 수 있고, 승인되어도 사용자의 데이터 삭제를 막지는 못한다. HTTPS/신뢰 가능한 보안 컨텍스트 조건도 확인한다.
- 동일 origin의 JavaScript가 읽을 수 있다. 기본적으로 애플리케이션 수준의 비밀 금고나 종단간 암호화 저장소는 아니다.
- 인덱스가 있다고 자연어 의미 검색을 해 주는 것은 아니다. 키워드 검색이나 임베딩 검색은 별도 기능이다.

공식 근거는 문서 마지막의 MDN 링크를 참고한다.

## 4. 목표 구조

```text
브라우저 IndexedDB
 ├─ 대화방 상태
 ├─ 메시지 원문
 ├─ 사용자가 명시적으로 저장한 기억
 └─ 검증된 경우에만 대화 요약
          │
          ├─ 화면: 최근 페이지 + 과거 더 보기
          │
          └─ 모델 입력: 범위 확인 → 검색 → 예산에 맞춰 선별
                             │
공통 규칙 + 화자/상대 + 캐릭터 카드 + 필요한 Lorebook
                             +
       최근 대화 + 관련 기억/과거 원문 + 현재 질문
                             │
                기존 AI 실행 경로로 전달
```

### 4.1 네 종류를 혼동하지 않기

| 종류               | 용도                          | 이번 작업                                         |
| ------------------ | ----------------------------- | ------------------------------------------------- |
| 대화/기억 DB       | 과거 사실을 다시 찾기         | IndexedDB로 구현                                  |
| 설정/Lorebook      | 세계관·소속·개인 설정         | 기존 authored 자료 재사용                         |
| 모델 다운로드 캐시 | 모델을 다시 다운로드하지 않기 | 현재 엔진의 관리 방식 유지                        |
| KV 캐시            | 모델 계산을 재사용            | 장기 기억으로 저장하지 않음. MVP 최적화 대상 아님 |

메모리는 모델 가중치를 업데이트하지 않는다. 또한 입력을 줄여도 긴 답변 자체의 생성 비용은 남으므로 출력 길이 제한은 별도로 유지한다.

### 4.2 처음 만들 최소 모듈

- `src/lib/chat/store.ts` — 예정. IndexedDB 연결·트랜잭션·대화 저장·이관을 담당하는 단일 저장 경로.
- `src/lib/chat/memory.ts` — 예정. 범위 필터·검색 결과 선별·기억 상태·입력 예산 처리를 담당. 가능한 로직은 순수 함수로 작성.

- 브라우저 표준 IndexedDB를 사용한다. 앱 런타임에 Dexie, 벡터 DB, 별도 메모리 서버를 필수 의존성으로 넣지 않는다.

## 5. 데이터 구조와 신뢰 규칙

### 5.1 object store 도입 순서

DB 이름 예시: `molu-chat-memory`.

| 도입 단계      | Store       | 핵심 내용                                                                      |
| -------------- | ----------- | ------------------------------------------------------------------------------ |
| P1 / schema v1 | `meta`      | 이관 상태·버전·원본 snapshot 식별 정보                                         |
| P1 / schema v1 | `rooms`     | 로컬 프로필/방 ID, 캐릭터, 참여자, 순서 카운터, 스크립트 진행도, 변경 revision |
| P1 / schema v1 | `messages`  | 안정적인 ID, 방, 실제 화자, 원문, 순서, 시간, 출처, 상태, 답변 대상 ID         |
| P3 / schema v2 | `memories`  | 명시적 기억, 공개 범위, 출처 메시지 ID, 생성/수정/만료 정보                    |
| P6 / 필요할 때 | `summaries` | 요약 본문, 원문 ID/범위, 커버한 순서, 자료 revision, 요약 방식                 |

구현 시 정확한 버전 번호는 실제 변경 순서에 맞춰 고정한다. 미래 기능의 빈 store를 모두 미리 만들지는 않는다.

### 5.2 메시지 필드의 의미

- `id`: 재시도해도 같은 사용자 메시지를 구분할 수 있는 안정적인 ID.
- `profileId`: 로컬 프로필 범위. 현재 단일 사용자라면 로컬 범위 하나로 시작하며 로그인 시스템은 만들지 않는다.
- `roomId`, `speakerId`, `speakerType`: 방과 실제 발화자. `user`, `character`, `app`의 의미를 구분한다.
- `seq`: 방 안의 안정적인 순서. 방 카운터 갱신과 메시지 저장을 같은 트랜잭션에서 처리한다.
- `createdAt`: 신규 메시지는 실제 전송 시각. 레거시는 날짜를 알 수 없으므로 null 허용.
- `legacyTimeLabel`, `importedAt`: 기존 `HH:mm` 표시와 이관 시각을 구분. 이관 시각을 과거 발송일로 위장하지 않는다.
- `sourceKind`: 사용자 입력, 모델 출력, 스크립트 대사, 앱 데이터, 출처 불명 레거시 등.
- `status`, `replyToMessageId`: pending/완료/실패/취소/중단 상태와 답변 대상.

주요 인덱스는 `[profileId, roomId, seq]` 등 방별 페이지 조회용이다. 미래 그룹 대화에서는 메시지 당시 참여자/수신 범위도 명확하게 다뤄야 하며, 단순히 모든 학생 발화를 같은 assistant로 합치지 않는다.

### 5.3 무엇을 사실로 취급할 것인가

| 자료                                   | 취급                                                      |
| -------------------------------------- | --------------------------------------------------------- |
| 앱이 실제로 제공한 현재 일정/실행 결과 | 해당 시점의 앱 사실                                       |
| 사용자가 직접 저장·확인한 메모         | 사용자 진술/확인한 기억. 앱에 등록된 일정이라는 뜻은 아님 |
| 과거 사용자 메시지                     | 그 사용자가 그렇게 말한 기록                              |
| 모델의 과거 답변                       | 모델이 그렇게 말한 기록. 사용자 사실로 자동 승격하지 않음 |
| 생성된 요약                            | 파생 자료. 원문과 동등한 사실 원본이 아님                 |

일정은 가능하면 캘린더의 실제 레코드를 다시 참조한다. “대화에서 약속 시간을 말함”과 “앱에 일정이 등록됨”을 혼동하지 않는다.

### 5.4 공유·수정·삭제

- 기본 공개 범위는 **해당 방 비공개**. 같은 학교/동아리라는 이유로 대화가 공유되지 않는다.
- 공통 기억은 사용자가 명시적으로 공유한 항목만 사용한다.
- 검색/랭킹 **전에** 프로필·방·공유 범위를 필터링한다.
- 첫 버전은 1:1 대화다. 그룹 대화가 추가될 때 새 참여자가 과거 비공개 기록을 자동으로 알게 하지 않는 별도 정책이 필요하다.
- 원문 삭제 시 이를 근거로 한 기억·요약·검색용 파생 자료를 함께 무효화한다. 다른 방에 공유된 파생 기억도 출처 삭제를 반영한다.
- 명시적 기억 삭제는 자동 검색으로 즉시 되살아나지 않도록 사용 중지/제외 상태를 함께 고려한다. 기억에서 빼는 것과 원문 자체를 지우는 것을 UI에서 구분한다.
- 기록/기억 변경 시 관련 revision을 올린다. 이전 자료를 사용하던 생성 작업의 늦은 응답이 삭제된 내용을 다시 저장하지 못하게 한다.
- 방별 범위는 앱의 논리적 접근 제어이지, 같은 브라우저의 소유자나 XSS를 막는 암호화 경계는 아니다.

## 6. Phase별 구현 계획

### Phase 0 — 계약·회귀 기준 고정 (`TODO #18`)

**목표:** 저장소 교체로 기존 대화 동작이 바뀌지 않게 기준부터 세운다.

- [ ] 현재 `npm test` 결과와 대표 브라우저의 기록 조회/입력 크기 기준 기록.

### Phase 1 — IndexedDB 저장소·안전한 이관 (`TODO #19`)

**목표:** 현재 남아 있는 기록을 손실·중복 없이 옮기고 메시지 단위 저장을 제공한다.

- [ ] `meta`, `rooms`, `messages`와 인덱스/버전 업그레이드 구현.
- [ ] DB 저장의 성공은 개별 request 성공이 아니라 transaction 완료로 확인.
- [ ] `error`, `abort`, `blocked`, `versionchange`, 예상하지 못한 연결 종료 처리.
- [ ] 네트워크/LLM 대기나 외부 비동기 가공을 긴 DB 트랜잭션 안에 넣지 않음.
- [ ] 배열형 레거시 → 아로나 방, 객체형 레거시 → 각 원래 방으로 매핑.
- [ ] 이관에 사용할 원본 snapshot을 고정하고 정규화·검증한 뒤 결정적인 legacy 식별자로 중복 방지.
- [ ] 이관 데이터와 완료 마커를 원자적으로 기록하고 재조회 검증.
- [ ] 기존 key를 즉시 삭제하지 않고 복구 원본으로 보존. 손상 레코드는 무시하고 성공 처리하지 말고 격리/개수/사유를 표시.
- [ ] 알 수 없는 방 ID는 임의로 아로나 방으로 합치지 않음.
- [ ] 기존 `HH:mm`에서 실제 날짜·시간대를 추측하지 않음.
- [ ] 다른 탭의 레거시 변경 감지와 이관 중 송신 차단/충돌 안내.

**주의:** localStorage와 IndexedDB를 함께 묶는 단일 트랜잭션은 없다. 두 저장소를 계속 양방향 동기화하는 방식은 사용하지 않는다. 전환 상태와 원본 변경을 검증하고 충돌을 표시한다.

**완료 기준:** 두 레거시 형식, 중간 실패, 재실행, 손상 입력, 다른 탭 변경에 대한 테스트 통과. 남아 있던 유효 기록의 내용·순서 보존과 중복 0건. 이미 60개 제한으로 사라진 과거 기록은 복원 대상으로 주장하지 않음.

### Phase 2 — 모모톡 연결·기록 생명주기 (`TODO #20`)

**상태: 구현·검증 완료(2026-10).** 실제 앱 화면·생성 흐름이 새 저장소를 사용한다. 아래 항목의 완료 여부는 [chat-memory-progress.md](chat-memory-progress.md)에 정리했다.

**목표:** 화면과 생성 흐름이 새 저장소를 사용하고, 이관 이후에도 데이터 유실을 막는다.

- [ ] DB 초기 읽기가 끝나기 전에는 로딩 상태를 표시하고 송신/최초 인사 중복 생성을 막음.
- [ ] 방별 최근 페이지를 읽고 과거 기록을 추가 조회. 전체 기록을 항상 `momoRooms`나 DOM에 적재하지 않음.
- [ ] `postMomo`와 pending/완료/취소/재시도 경로를 안정적인 메시지 ID 기준으로 전환.
- [ ] 사용자 메시지는 생성 시작 전 저장. assistant 응답은 완료 시 저장. 스트리밍 토큰마다 전체 대화를 쓰지 않음.
- [ ] 중단 응답은 완료 대화나 사실 기억으로 취급하지 않음. 같은 요청의 중복 완료를 방지.
- [ ] 화면 변경/방 변경/삭제/새 작업 이후 늦은 응답은 기존 작업 식별자와 revision으로 거부.
- [ ] 방 순서·스크립트 진행도·메시지 상태 등 연관 변경을 한 트랜잭션에서 처리.
- [ ] `pendingTopic()`을 화면에 로드한 메시지 개수에서 분리. 이관 당시 진행도를 보존하고 이후 진도 규칙을 명시.
- [ ] 다중 탭의 동시 갱신을 처리. 같은 방의 생성 충돌은 감지·거부하고 안내하며, BroadcastChannel만을 잠금처럼 사용하지 않음.
- [ ] 저장 실패 시 “저장됨”으로 표시하지 않고 재시도/내보내기를 제공.
- [ ] 이관 이후 DB 장애를 조용한 localStorage 쓰기로 우회하지 않음. 명시적 일시 모드라면 새로고침 유실 가능성을 표시.
- [ ] 기본 JSON 백업/복원 구현. 포맷 버전·크기·ID·필드·중복·참조를 검증하고 자동 덮어쓰기 방지.
- [ ] 방별/전체 삭제와 기존 전체 초기화를 IndexedDB·레거시 원본·파생 자료까지 연결. 삭제 성공 전에 무조건 reload하지 않음.
- [ ] 모델 캐시 삭제와 대화/기억 삭제를 다른 동작으로 유지.
- [ ] 새 JS 모듈을 `server.js` 서빙 목록에 추가하고 import 경로 회귀 검사.

**완료 기준:** 새로고침 후 원문·진행도 유지, 페이지 추가 조회 순서 유지, 취소/재시도 중복 0건, 삭제 중 늦게 도착한 응답으로 데이터 부활 0건. 화면에 많은 기록을 한꺼번에 붙이지 않음.

### Phase 4 — 모델 입력 연결·문맥 예산 (`TODO #22`)

**목표:** 원문이 늘어도 모델에 보내는 입력량은 제한한다.

- [ ] 역할/캐릭터/필요한 설정과 최근 대화, 선별된 기억·원문을 조립.

- [ ] 실제 입력 예산은 아래 식으로 관리.

```text
사용 가능 문맥 = 실제 모델 한도 - 출력 예약 - 안전 여유
실제 입력 = 채팅 템플릿 + 운영 규칙 + 카드 + Lorebook
          + 예시 + 선택된 과거 대화 + 기억/원문 + 현재 질문
```

- [ ] 초과 시 관련성 낮은 참고 정보·오래된 대화 등을 완결된 항목 단위로 제거. 최신 질문·화자 정의·핵심 제약은 임의로 자르지 않음.
- [ ] 질문에 필요한 현재 앱 사실을 장식적인 배경보다 우선. 필수 내용만으로도 초과하면 명확한 오류/입력 축소 안내.
- [ ] 정확한 토큰 계산이 가능한 백엔드는 이를 사용. 불가능하면 안전한 운용 범위를 검증하기 전 문맥 확대를 하지 않고, 문자 수를 토큰 수라고 표시하지 않음.
- [ ] Worker에 개수/길이/형식이 제한된 memory DTO를 추가. 임의의 system 메시지나 클라이언트 제공 캐릭터 예시를 허용하는 우회는 만들지 않음.
- [ ] 기억은 인용된 참고 자료로 구분하고 운영 지시로 취급하지 않음. 이것만으로 모든 프롬프트 공격이 해결된다고 주장하지 않음.
- [ ] 실제 발화자·대상과 캐릭터 ID/방/작업 revision 일치 확인.
- [ ] 현재 KV 초기화 유지. 다른 방·다른 LoRA의 KV를 공유하지 않음.
- [ ] 어떤 자료가 선택/제외됐는지 개발용 추적 기능 제공. 민감한 전체 대화를 무조건 콘솔/외부 로그로 보내지 않음.

**완료 기준:** 원문 1만 개가 있어도 전체 원문을 프롬프트에 넣지 않음. 조립 후 예산 검사 통과. 범위 밖의 기억·임의 system·폐기된 작업 입력이 전달되지 않음. 검색되지 않은 내용을 모델이 기억한다고 가정하지 않음.

| 기존 배열형/방별 객체형 데이터         | 원래 방·내용·순서 보존                                                       |
| 이관 중 종료 후 재실행                 | 중복 없음, 완료되지 않은 이관을 성공으로 취급하지 않음                       |
| 날짜 없는 `HH:mm` 기록                 | 날짜를 창작하지 않음                                                         |
| 방에 1만 메시지                        | 화면/모델에는 제한된 부분만 읽음                                             |
| 답변 생성 중 취소·방 변경·재시도       | 중복 최종 응답이나 다른 방 저장 없음                                         |
| 생성 중 방/기억 삭제                   | 늦은 결과로 삭제 정보 부활 없음                                              |
| 서로 다른 탭에서 같은 방 변경          | 순서/ID 충돌과 오래된 결과 쓰기 방지                                         |
| 유우카 방의 비공개 기억 → 미카 요청    | 모델 입력에 포함되지 않음                                                    |
| 사용자가 명시적으로 공유한 항목        | 허용한 범위에서만 조회                                                       |
| 모델만 언급한 가짜 10시 약속           | 사용자 일정 사실로 저장하지 않음                                             |
| 사용자가 이전 메모를 수정              | 활성 기억에는 수정 반영, 예전 원문은 과거 진술로 구분                        |
| 기억/출처 삭제                         | 관련 요약·검색 자료에서도 제외                                               |
| 용량 부족·persist 거부·비공개 모드     | 데이터 보존 한계를 명확히 알림                                               |
| 모델 캐시만 삭제                       | 대화·기억 유지                                                               |
| 앱 전체 데이터 초기화                  | 대화·기억·파생 자료·레거시 재이관 경로까지 정리                              |
| 백업 파일에 임의 지시/HTML/잘못된 역할 | 실행하지 않고 데이터 검증/안전한 텍스트 표시 적용                            |
| 토큰 예산 초과                         | 선택 자료를 줄이거나 오류를 표시, 필수 입력을 조용히 잘라 의미를 바꾸지 않음 |

## 9. 하지 않을 것

- 전체 대화를 매번 프롬프트에 붙이기.
- 저장 데이터 압축만으로 모델 입력 비용이 해결된다고 설명하기.
- 매 턴 전체 대화를 모델로 재요약하기.
- 모델의 발화를 검증 없이 장기 사실로 확정하기.
- 학교/동아리가 같다는 이유로 사적인 대화 공유하기.
- 대화 기록을 LoRA에 계속 재학습시키기.
- 첫 버전에 벡터 DB·클라우드 동기화·대규모 기억 에이전트 도입하기.
- localStorage와 IndexedDB의 조용한 이중 쓰기/자동 fallback으로 유실을 숨기기.
- 브라우저 DB가 영구 보존·암호화·다중 기기 동기화를 보장한다고 주장하기.
- 메모리 도입으로 현재 캐릭터 말투/역할 문제가 해결됐다고 미리 판정하기.
